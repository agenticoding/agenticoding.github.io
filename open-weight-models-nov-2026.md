# Open-Weight Models Source Catalog — November 2026

Sources checked through **2026-11-19**. A context cap is not a throughput guarantee.

- **Organization:** United States, China, and France; sorted by lab, then by total parameters within each lab.
- **Parameters:** total / active for MoE. Gemma 4 E2B/E4B use per-layer embeddings (PLE); their effective parameter counts are not MoE active counts.
- **Modality:** the checkpoint's documented input and output channels from its model card: `text`, `image`, `audio`, `video`. `text+image → text` reads as input channels become output channels. Video counts when the card states video input, frame-sampled video included. The column describes the architecture, not every artifact: a text-only GGUF of a multimodal checkpoint stays text-only.
- **Memory:** checkpoint sizes are on disk, in decimal GB unless marked GiB. Country tables list checkpoint and runtime notes; use the [hardware fit table](#hardware-fit--64k-to-reference-path-maximum) for calculated budgets. Raw KV is not runtime memory. `?` means no runtime total or rate is established for the stated path.
- **Context:** native checkpoint limit unless labeled as an extension. Context caps include prompt **plus** output.
- **Speed:** `out` counts generated tokens; `total` includes input. `/user` is per request; aggregate rates are across requests and use `/GPU` only when normalized. `c` is concurrency. Separate operating points, offload runs, and speculative decoding are labeled. No cloud service rates qualify as on-prem evidence.
- **License:** open-weight does not mean open-source or unrestricted hosting. Check the exact checkpoint terms.

### Streamed layouts — host RAM and SSD

A streamed layout holds a checkpoint the accelerator cannot. A floor is a floor: the WARP figures are the stated hard minimum at 4K and the DwarfStar plan is a 1,024-token run. Grown to a longer context, each floor carries the checkpoint's own cache cost. Host RAM is a separate tier from the accelerator budget, and a machine that publishes neither cannot be sized for these layouts. ### Platform support highlights

- **NVIDIA:** RTX 4090/5090 are 24/32 GB; RTX PRO 5000/6000 Blackwell are [48 GB](https://www.nvidia.com/en-us/products/workstations/professional-desktop-gpus/rtx-pro-5000/) and [96 GB](https://www.nvidia.com/en-us/products/workstations/professional-desktop-gpus/rtx-pro-6000/). Below them, the [RTX 3060](https://www.nvidia.com/en-us/geforce/graphics-cards/30-series/rtx-3060-3060ti/) carries 12 GB, the [RTX 5060 Ti](https://www.nvidia.com/en-us/geforce/graphics-cards/50-series/rtx-5060-family/) 16 GB, and the [RTX 3090](https://www.nvidia.com/en-us/geforce/graphics-cards/30-series/rtx-3090-3090ti/) 24 GB; screen them at **10/14/22 GiB**, the same 2 GiB reserve the cards above give up. [DGX Spark][spark-hw] offers a 128 GB unified-memory SKU at 273 GB/s with ConnectX-7; the OS shares that memory. Eight 80 GB H100s or 141 GB H200s provide nominal 640 or 1,128 GB. ## Hardware fit — 64K to reference-path maximum

**Read the memory numbers first.** If a model needs 14 GiB, any compatible accelerator with 14 GiB free meets that estimate. A bigger card does not need a new estimate. A different precision, engine, or layout can change the number. Two Sparks are not one 256 GB GPU: each device must hold its assigned weights, cache, and buffers.

One resident text request, prompt plus output; no CPU/SSD offload. `K` = 1,024 tokens; `1M` = 1,048,576 here. The final anchor stops at the reference path's cap when it is lower than the checkpoint limit (Mistral and MiniMax). A single hardware entry covers both contexts; an arrow shows a change. **`est`** = calculated with a runtime allowance; **`cfg`** = published launch cap, not a full-length test; **`validated`** = source verifies that context fits; **`check`** = memory candidate or prior-revision recipe that needs a launch check. A number followed by `+` is a **subtotal** with allocations still to budget, not a standalone fit estimate.

**Hardware key.** Screen nominal 24/32/48/96 GB RTX cards (4090 / 5090 / RTX PRO 5000 / RTX PRO 6000) at **22/30/46/94 GiB**. **Byte accounting.** Divide bytes by `2^30` for GiB. Start with the exact artifact, not active parameter count. Add one request's KV/state and any required draft weights. Shard only what the stated layout shards; charge replicated data to each rank. Add local graph, allocator, and workspace costs. If the engine reserves cache pools, compare the allocations, not only the occupied KV. Retest with the production batch, concurrency, vision, and speculation settings.

**llama.cpp.** Add **3 GiB** for buffers and recurrent state; assume Flash Attention and a 512-token microbatch. For each cache-bearing layer use `2 × bytes per element × KV heads × head width × retained tokens`. Use FP16 except for Qwen3.8, which uses [Q4_0 (18 bytes per 32 elements)](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-common.h#L194-L199). Full layers retain every token; sliding layers retain at most the [window plus microbatch, padded to 256](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-kv-cache-iswa.cpp#L69-L78). Read the file size and layout from the linked GGUF (`api/models/<repo>?blobs=true` gives file sizes). For Gemma E2B/E4B count [shared cache once](https://github.com/ggml-org/llama.cpp/blob/master/src/models/gemma4.cpp#L8-L18). Arete uses 16 full layers (4 heads × 256); Laguna XS uses 10 full and 30 windowed (8 × 128, window 512).

Nemotron uses 75.01 GB and eight cache-bearing layers (2 × 128, FP8); add SSM state and any draft/profile pools. The 91 GB recipe figure is not a measured 1M peak. The [DwarfStar Q4 path](https://github.com/antirez/ds4/blob/HEAD/docs/MODELS.md#L86-L108) uses the previous V4.1 Flash release, not 1017. It needs a 512 GB Mac to hold the main weights, or SSD streaming on smaller Macs.

**Levers with no published figure.** The [8×H100 vLLM recipe][ds41-recipe] needs ~183 GiB of pinned host RAM for Engram; the [four-Spark gr8 path][gr8-ds-engram] reads Engram from local NVMe. Neither is resident. DwarfStar's V4 Pro Q2 target states a 512 GB machine or SSD streaming, with no held figure. Size speculative decoding as separate weights and cache; a short DSpark test is not a long-context memory test. Kimi K3 DCP partitions MLA KV, not KDA state; K3.1's cache layout differs and has separate [AMD Instinct recipes](https://docs.sglang.io/cookbook/autoregressive/Moonshotai/Kimi-K3.1-Pro.md). [Glimmer's GGUF](https://huggingface.co/meta-models/Muse-Glimmer-30B-GGUF) targets 24 GB, and its sample server's aggregate context across slots is not a per-slot maximum. [PulsarMLX](https://github.com/MahdiHedhli/PulsarMLX/blob/HEAD/README.md#L67-L88) reports ~2.6–4.2 out on a 128 GB M1 Ultra with a 181.9 GB artifact; this is a paged research path.

### Apple Silicon (MLX) — parallel track

Budget for weights, engine buffers, and KV after leaving memory for macOS. A Mac's usable pool is not the capacity printed on the box. A checkpoint tag or generation result does not prove its maximum context fits.

- **Resident, one Mac:** select a local quant for gpt-oss, Gemma 4, Qwen, or Laguna XS. [Glimmer's measured Mac path][glimmer-card] is ExecuTorch; the [Muse Spark Open 512 GB M3 Ultra runs][muse-mac] use llama.cpp and MLX with different quants. Do not apply the server NVFP4 footprint to these results.
- **Distributed Macs:** [Meta's Muse Spark setup][muse-meta] uses two 512 GB M5 Ultra Mac Studios via MLX/JACCL over Thunderbolt 5. Model sharding and the interconnect must both be supported.
- **SSD/host-streamed:** the PulsarMLX and WARP results above buy capacity at a decode cost. Size the SSD artifact and memory separately; neither result validates a full-resident fit.

## Networked cluster deployment

- **vLLM** — [Ray or multiprocessing](https://github.com/vllm-project/vllm/blob/main/docs/serving/parallelism_scaling.md#L139-L158) for supported multi-node recipes. Start with TP within a fast interconnect domain and use the model recipe for PP, DP, or EP across nodes. Elastic EP is a separate Ray DP feature. For OOM, inspect weights, graphs, and KV allocations before tuning the context or utilization limit.
- **SGLang** — use the recipe's TP/PP/DP/EP layout, node count, rank, and init address. [DCP](https://docs.sglang.io/docs/advanced_features/dcp.md) is decode context parallelism within an attention TP group, not replica DP. [Mooncake](https://docs.sglang.io/docs/advanced_features/pd_disaggregation.md) can transfer KV in supported P/D layouts.
- **TensorRT-LLM** — NVIDIA-only; [single- and multi-node serving](https://nvidia.github.io/TensorRT-LLM/examples/llm_mgmn_trtllm_serve.html) depend on the recipe. NIM can use a different backend; check the container metadata before assuming it runs TensorRT-LLM.
- **llama.cpp** — [RPC](https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md) can split GPU tensors across hosts over TCP/RDMA. It is a proof of concept, not a production boundary. Do not expose it on an open network or use it in a sensitive environment.
- **Ollama** — use the released single-machine multi-GPU path. [`OLLAMA_RPC_SERVERS`](https://github.com/ollama/ollama/pull/16137) and [`ollama rpc`](https://github.com/ollama/ollama/pull/10844) come from separate proposals; do not plan a cluster around them.
- **MLX** — [JACCL][mlx-distributed] requires macOS 26.2+, Thunderbolt 5, and direct pairwise links for the documented topology. TCP ring is a separate path. Confirm model sharding in [MLX LM](https://github.com/ml-explore/mlx-lm/blob/main/README.md#L14) before adding Macs.
- **Model-to-cluster patterns** — [Mistral FP8][mistral-recipe] uses two 8×H200 nodes in the linked recipe; [Inkling 2 NVFP4][inkling2-recipe] reaches 1M with TP8 across two GB200 trays. [DeepSeek V4 Pro 0813][dspro-recipe] caps at 800K on the specified 8×H200 layout and has a single-node B300 layout. These counts describe recipes, not a rule for how context scales with nodes. For Spark, [NVIDIA's guided setup][spark-cluster] uses ConnectX-7 and a switch for four devices.
